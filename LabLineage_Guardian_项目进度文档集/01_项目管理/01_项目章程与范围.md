# 项目章程与范围

## 1. 项目使命

构建一个能够回答“这张图和这个结论是怎么来的、还能不能重新跑出来、缺了什么、哪些结果需要人工处理”的科研证据链与离组交接系统。

## 2. 核心问题

- 数据和运行结果位于组内服务器，服务器可能受限联网或完全离线；
- 代码位于 GitHub，但真实运行版本可能是服务器上的未提交副本；
- 许多科研目录没有 Git，重要修改只能依靠文件副本和时间戳猜测；
- 图像、参数、日志、数据模组、论文结论之间缺少明确关系；
- 大量失败、重复、过期、探索性结果混杂，接手人无法判断价值；
- 传统“检查有没有 README”无法证明关键结果可复现。

## 3. 产品目标

1. 为关键结论建立 `结论 → 图表 → 输出 → 运行 → 参数 → 代码 → 环境 → 数据` 的证据链；
2. 支持联网、单向出站和完全离线三种组服务器模式；
3. 支持 GitHub 与无 Git 目录并存；
4. 从接入时刻开始持续记录无 Git 文件变化；
5. 给出 R0–R4 可复现等级和带证据的 Finding；
6. 通过 Gemini Enterprise Agent Platform 解释、治理和部署 Agent；
7. 通过 Drive、Sheets、Gmail 完成交接报告、台账和人工协作；
8. 量化减少来源查找时间、提高缺陷发现率和复现准备度。

## 4. 范围

### 4.1 第一发布范围

- Linux/POSIX 组服务器目录；
- GitHub 仓库只读接入；
- Python、Notebook、YAML/JSON/TOML、常见日志和图像元数据；
- 文件哈希、快照、无 Git diff、离线签名 Bundle；
- PostgreSQL 数据模型、导入 API 和谱系查询；
- R0–R3 自动判断，R4 只在真实重跑后产生；
- duplicate/orphan/failed/stale/manual-edit 等结果风险；
- ADK Agent、Agent Runtime、Agent Registry、Agent Gateway；
- Google Drive 报告、Sheets 台账、Gmail 草稿；
- 人工确认和审计日志。

### 4.2 明确非目标

- 不替代 Git、DVC、MLflow、W&B、Snakemake、Nextflow；
- 不证明科学结论本身正确；
- 不自动执行未知科研代码；
- 不完美恢复首次扫描前已经丢失的历史；
- 不自动删除垃圾文件；
- 不将全部原始数据迁移至 Google Cloud 或 Drive；
- 不在首个版本覆盖所有语言、调度器和实验平台；
- 不为展示平台能力而强行引入 AlphaEvolve。

## 5. 成功标准

| 类别 | 成功标准 |
| --- | --- |
| 用户价值 | 接手者能够在 2 分钟内定位一张关键图的主要代码、数据、参数和缺口 |
| 可追溯 | 所有 Agent 关键判断均可回到 evidence ID 和确定性工具结果 |
| 隐私 | 默认流程不上传原始数据；未授权原始内容外传为 0 |
| 无 Git | 两次快照间新增、修改、删除准确追踪，移动以候选形式呈现 |
| GitHub 对齐 | 能发现服务器代码与具体 commit SHA 不一致 |
| 结果筛选 | 能够区分正式采用、候选、探索、重复、失败、过期和疑似垃圾 |
| 平台执行 | ADK Agent 在 Runtime 部署，Registry 登记，Gateway 对工具调用实施 allow/deny |
| 协作闭环 | 可写入 Sheet、导出 Drive 报告、创建 Gmail 草稿且均有人工确认 |
| 量化影响 | 形成查找时间、缺陷召回、误报、R 等级提升和人工往返次数的可复核数据 |

## 6. 项目约束

- 比赛资源的具体额度、有效期、区域与权限以组委会最终通知为准；
- 不能假定 Agent Platform 所有功能在所选区域都可用，必须做 Spike；
- 组服务器可能没有出站网络，只能导出签名包；
- 真实科研数据可能存在未发表、合作、伦理或个人信息限制；
- 项目团队人数未冻结，任务以角色而非姓名分配；
- 计划周期使用相对周次，便于匹配实际截止日期。

## 7. 章程批准条件

- 项目负责人、技术负责人、科研流程顾问确认范围；
- 比赛资源未知项已登记而非被默认为可用；
- 关键指标有测量方式；
- 三条核心用户旅程已成为优先级最高的端到端路径；
- P0/P1 风险有负责人。
