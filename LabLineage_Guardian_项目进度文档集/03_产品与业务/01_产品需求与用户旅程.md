# 产品需求与用户旅程

## 1. 核心用户故事

### US-01：图像来源追踪

作为接手人，我想知道论文图 3 由什么脚本、参数、代码版本、环境和数据生成，以便判断能否复现。

### US-02：代码版本冲突

作为离组人员，我想发现服务器真实运行脚本与 GitHub commit 的差异，以便在离组前保存未提交修改。

### US-03：无 Git 更新记录

作为课题组管理员，我希望从系统接入开始记录目录变化，即使项目没有 Git，也不再继续丢失修改记录。

### US-04：数据模组梳理

作为新成员，我想看到 raw、processed、simulation、paper-results 等模组之间的关系和未知连接。

### US-05：结果筛选

作为导师，我想区分正式采用、探索、重复、失败、过期和疑似垃圾结果，但不希望系统未经确认删除任何文件。

### US-06：离线交接

作为受限服务器管理员，我希望生成不含原始数据的签名清单，经人工传入云端后仍可完成主要审计。

### US-07：交接协作

作为科研秘书，我希望把审计状态写入 Sheet、将报告保存到 Drive，并生成待确认的 Gmail 整改草稿。

## 2. 三条主旅程

### 旅程 A：追踪关键图

```text
选择项目和图像
→ 查询候选谱系
→ 展示证据强度
→ 发现代码/参数/环境缺口
→ 人工确认正确来源
→ 生成整改任务
```

### 旅程 B：无 Git 目录变更

```text
首次扫描建立基线
→ 文件修改/移动/新增
→ 第二次扫描
→ 生成快照 diff
→ 用户确认移动候选
→ 更新记录进入交接报告
```

### 旅程 C：离组交接

```text
注册服务器/GitHub/Workspace 来源
→ 导入最新快照
→ 自动谱系和审计
→ 处理 P0/P1
→ 接手人确认关键结论
→ 导师审核
→ 输出报告、Sheet、Gmail 草稿
```

## 3. 产品原则

- 证据比答案重要；
- 推断必须显式标注；
- 缺数据时承认不知道；
- 不因文件名“final”就判断正式采用；
- 不把失败实验都叫垃圾；
- 不自动删除；
- 不强迫数据上云；
- 对非技术接手者使用可理解语言，同时保留技术证据。
